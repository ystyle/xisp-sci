# 性能与基准

所有数字来自 `bench` 成员的实测（`bench/report.md`），可复现。

## ⚠️ 必须开 `-O2`

**同一个 `matmul`，加与不加差 8~68 倍。**

| n | `-O2` | 默认 | 倍数 |
|---|---|---|---|
| 50 | 0.63 ms | 5.19 ms | 8× |
| 200 | 11.3 ms | 216 ms | 19× |
| 400 | 69.6 ms | 1.69 s | 24× |
| 600 | 210 ms | 14.3 s | **68×** |
| 1000 | 967 ms | **29.4 s** | 30× |

不是「快一点」，是换了个数量级。`n > 400` 之后基本不可用。

```toml
[package]
  compile-option = "-O2"
```

发布出来的是**源码包**，下游在自己的工程里编译，不加 `-O2` 就得不到上表的性能，
**而且不会有任何警告**。

## matmul 规模扫描

纯仓颉，无 BLAS：

| n | 耗时 | GFLOPS |
|---|---|---|
| 50 | 0.6 ms | 0.43 |
| 100 | 2.8 ms | 0.72 |
| 200 | 11 ms | 1.46 |
| 400 | 69 ms | 1.85 |
| 600 | 207 ms | 2.08 |
| 800 | 470 ms | 2.18 |
| 1000 | 1.0 s | 1.97 |

GFLOPS 随规模升到约 2 后趋平：小规模时解释器开销占主导，大规模时计算占主导。

对比 OpenBLAS 单核（50~100 GFLOPS）差 25~50 倍。**对 n < 1000 的数据分析够用**。

## 三个后端的差异

本套件的计算主体是仓颉代码（ndarray 运算、FFT、矩阵分解），那部分与 xisp 用哪个后端无关。
后端只影响**脚本层**：函数调用、递归、变量查找。

| 场景 | AST | BC | JIT |
|---|---|---|---|
| `matmul` 800×800 | 507 ms | 500 ms | 483 ms |
| `fft` 8192 点 | 401 µs | 407 µs | 432 µs |
| `std` 10 万元素 | 5.53 ms | 5.29 ms | 5.67 ms |

差在噪声内。想让这些数字变小，只有 `-O2` 或接 BLAS 两条路，换后端没用。

### 但 AST 有栈深上限

| 后端 | `rep(1000)` | `rep(20000)` |
|---|---|---|
| AST | ❌ **栈溢出** | ❌ 栈溢出 |
| BC | 10.5 ms | 137 ms |
| JIT | 3.5 ms | 234 ms |

AST 求值器用**宿主语言的调用栈**递归下降，深度上限 1000 层，超过报
`Maximum stack depth exceeded`。BC / JIT 走显式栈帧，不受这个限制。

这不是性能问题，是**能不能跑**的问题：

- **纯数组管道**（本套件的主要用法）不涉及深递归 —— AST 完全够用
- 脚本里写了**深递归**，或者拿**尾递归当循环** —— 必须上 BC/JIT

所以选后端的依据是「需要不需要深递归」，不是「哪个快」。

## 稀疏矩阵的代价

Matrix Market 真实矩阵，用**稠密表示**：

| 矩阵 | 形状 | 非零 | 稠密元素 | 浪费 | 稠密 matmul |
|---|---|---|---|---|---|
| `gent113` | 113×113 | 655 | 12 769 | 19.5× | 3.0 ms |
| `will199` | 199×199 | 701 | 39 601 | 56.5× | 10.2 ms |
| `ash292` | 292×292 | 1 250 | 85 264 | **68.2×** | 28.0 ms |
| `ash331` | 331×104 | 662 | 34 424 | 52.0× | 非方阵 |

**稠密表示的工作量是 `n²`，与 `nnz` 无关**。所以没做稀疏类型，
见[设计取舍](/reference/design#不做稀疏矩阵)。
