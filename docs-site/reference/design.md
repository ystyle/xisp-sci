# 设计取舍

这份文档记录为什么这样设计，以及被放弃的替代方案。

## 数组是外部值，不是核心类型

`LispValue` 是封闭枚举。加 `Array` 变体意味着动核心的判别式，所有 `match` 都要改，
且每加一种外部结构（稀疏矩阵、DataFrame、图）就要再动一次。

所以走 `LispExternal` 通道：核心定义一组**能力接口**，外部值自己实现。

| 接口 | 提供什么 |
|---|---|
| `LispExternal` | 基座：类型名、显示 |
| `LispExternalEquatable` | `=` |
| `LispExternalIndexable` | `length` / `nth` |
| `LispExternalComparable` | `<` `>` |
| `LispExternalCallable` | 当函数调用 |
| `LispExternalArithmetic` | `+ - * /` |
| `LispExternalReducible` | `sum` / `max` / `min` / `product` |
| `LispExternalElementwise` | 全部标量数学（`sin` / `exp` / …） |

关键约定：**接口方法返回 `Option`，`None` 表示「不支持」**，核心随后抛 `TypeError`。
不允许用 `nil` 表示不支持，那样错误会变成静默的错值。

好处是这套通道对任何类型开放。数组实现了 `Elementwise`，就自动获得全部 17 个标量
数学函数，核心不需要知道「数组」存在。

## dtype 只有三种

`int64` / `float64` / `bool`。没有 complex、没有 int32、没有 decimal。

少而明确比多而模糊好。需要复数的地方用两个数组表示（`xisp_signal` 就是这么做的），
需要精确十进制的地方应该用专门的库，一个通用数组类型不该假装自己能覆盖这些。

## `length` 是元素总数

不是「第一维长度」。`nth` 是**扁平**下标，不是多维索引。

这两个约定是刻意与一维数组保持一致的：如果定义成「第一维长度」「按维度索引」，
同一个函数在 0 维、1 维、2 维数组上行为就变了，调用方每处都要判断。

## `[...]` 字面量仍是列表

`[1 2 3]` 是列表，不是数组。要数组必须显式 `cangjie::array`。

让字面量自动推断成其中一个，总有一类用法会写出意外的结果：列表可以嵌套任意结构，数组要求矩形。
显式转换虽然多敲几个字，但语义清楚。

## `std` 默认样本标准差

除 `n−1`。这与 NumPy 相反（`np.std` 默认 `ddof=0`）。

选样本作默认，是因为数据分析里手上的数据多数时候是样本。「我有的全部数据」这种
情形在真实工作中不常见。要总体标准差时显式用 `std-pop`。

这个约定必须写进文档，否则调用方会拿着和 NumPy 不同的结果去对账。

## 两套 NaN 语义

| 写法 | 语义 |
|---|---|
| `(max x)` | 数学：NaN 传播 |
| `(cangjie::max x)` | 数据分析：跳过 NaN |

不统一成一套，是因为两种用法都是对的：

- 数值计算里 NaN 就该传播，你能从 NaN 结果反推「输入里有坏值」；
- 数据分析里 NaN 是缺失，一批数据有一个空值就让最大值变 NaN 是不可接受的。

**加 `cangjie::` 前缀 = 数据分析语义**，这是整个套件的命名约定。

## 一族一个成员

`array` / `io` / `stats` / `linalg` / `signal` / `num` 六个成员，严格单向依赖
（都只依赖 `xisp` 核心，互不依赖）。

好处是只需要统计的宿主不必把 FFT 和线代拖进来。门面 `xisp_sci` 是唯一允许
「知道所有族」的地方，且只做聚合、不含重实现。

## 不接 BLAS / LAPACK

`cjpm` 没有可选依赖。接 C 库意味着每个宿主都得装 C 工具链，与「纯仓颉、零依赖」
的前提直接冲突。

代价是 `matmul` 1000×1000 约 1 秒 vs OpenBLAS 的 20 毫秒。但对 n < 1000 的
数据分析场景够用。

真需要性能时应该另开加速模块，不要把 C 依赖塞进本模块。

## 不做稀疏矩阵

Matrix Market 的真实稀疏矩阵测过：`ash292`（292×292，1250 非零）用稠密表示要处理
85264 个元素，**浪费 68 倍**。

但稠密乘法仍然只要 28 毫秒。而 CSR/CSC 要引入两套数据结构、与稠密互转、一套新的
索引语义，成本远大于当前收益。

判据：等真实数据出现 `n ≥ 1000 且稀疏度 < 5%` 的场景再说。

## 不做绘图

本套件只产出**可渲染的结构**（直方图边界与计数、箱线图五数、相关矩阵），不渲染。

引入图形依赖会让「一个数据分析库」变成「半个绘图库」：字体、坐标轴、颜色、交互、
导出格式……每一项都是独立复杂度，而且和数据分析本身没关系。

更重要的是，图表给谁看决定了它该长什么样。终端用 ASCII、网页用 Canvas、报告用 PDF，
同一个数据集需要三种完全不同的呈现。把这些塞进核心库，等于替调用方做了他们最清楚的
决定。

## 图表数据也不滥用函数

散点图、折线图没有专门函数，因为要的就是数据本身，两个 ndarray 直接交给前端。

只有真需要计算的（箱线图五数、相关矩阵）才提供函数。多一层没有信息量的抽象是有害的。
